## [2026-08-05] Title-over-featured-image overlay (v1.5.0)
- User request, well-scoped: an option to render the page title centered inside the featured image (semi-transparent background box, configurable font size and background color/opacity) instead of in the normal content flow, on Default/Boxed/Left/Right Sidebar page templates.
- Global setting (`title_overlay_enable` + `title_overlay_font_size` + `title_overlay_bg` + `title_overlay_bg_opacity`, GNN Panel → Pages Layout) sets the theme-wide default and shared visual style. A new **tri-state per-page override** (`_gnn_title_overlay` postmeta: `''` theme default / `'1'` force on / `'0'` force off, sanitized via `gnn_sanitize_tristate_meta()`) lets any individual page turn it on or off regardless of the theme-wide setting — the user specifically asked for "off site-wide, on for just 1-2 pages" to be possible. Resolved by `gnn_title_overlay_active()` in `inc/page-meta.php`, which also now short-circuits `gnn_hide_title()` so the normal in-flow `<h1>` never double-renders alongside the overlay.
- Rendering lives in `gnn_page_featured_image()` (`inc/page-layouts.php`): when active, an absolutely-positioned `.gnn-page-thumb__overlay` centers the title (flexbox, all sides) over `.gnn-page-thumb`, with font-size/background/opacity set via an inline `style` attribute per-render (background+opacity combined with `color-mix(in srgb, HEX opacity%, transparent)` — no wp-color-picker-alpha dependency, staying consistent with this session's "WordPress core only" stance) rather than threading new CSS custom properties through the enqueue pipeline, since these particular values aren't per-page-overridable.

## [2026-08-02] Fix sidebar/content top-alignment on page templates (v1.4.5)
- User-reported bug: on Left/Right Sidebar page templates, the sidebar sat visibly higher (56-69px) than the main content, and grew worse the more `content_top_padding` (GNN Panel → Pages Layout) diverged from its default. Root cause: `.gnn-page` (the page-template wrapper) already carries `padding-top: var(--gnn-content-top-pad, 50px)` as a grid container, which should top-align both grid children (`.site-main.content-area` and the sidebar `<aside>`) automatically — but `.site-main`'s own base rule (`padding-top: 56px; padding-bottom: 88px;`, meant for the plain blog/archive listing) was never zeroed out for this context, so it silently stacked an extra fixed padding on top of the dynamic one, pushing content down further than the sidebar. The user's own workaround (hardcoding `.widget-area { padding-top: 69px; }` to compensate) would have broken again the moment `content_top_padding` changed.
- Fixed with `.gnn-page > .site-main { padding-top: 0; padding-bottom: 0; }`, making `.gnn-page`'s own dynamic padding the single source of truth — exactly mirroring the identical fix already in place for the sibling `.content-sidebar-layout` system (`.content-sidebar-layout > .site-main { padding-top: 0; padding-bottom: 0; }`, same file). No new CSS variables, no hardcoded pixel values; alignment now holds at any configured spacing.

## [2026-08-02] Color-picker label, name-field overflow, preview styling (v1.4.4)
- User feedback round 2 on the panel restructure: (1) the "Select Color" text label on each swatch button was redundant — clicking the color itself should be enough. Hidden via the standard screen-reader-text visually-hidden pattern (not `display:none`, so it stays accessible) rather than `display:none`, which would have removed it from the accessibility tree. (2) Button Styles' name field used WP core's `.regular-text` (25em ≈ 400px), overflowing its 260px-minimum card — the user flagged not knowing what else that shared class affects elsewhere in the panel, so the fix scopes a width override to `.gnn-btn-style-card input.regular-text` only, leaving the global class untouched. (3) The button preview rendered as a bare, unstyled gray `<button>` regardless of configured colors — root cause: `.gnn-btn`'s actual pill-shape/padding/font-weight CSS lives in `main.css`, the front-end stylesheet, which is never enqueued on the wp-admin panel screen. Added a scoped `.gnn-btn-style-card__preview .gnn-btn` rule mirroring that base styling (with a black/white fallback), so the per-style inline `style` attribute still wins for the actual configured colors but the shape now renders correctly too.

## [2026-08-02] Fix color-picker swatch rendering (v1.4.3)
- User-reported bug from a live screenshot of v1.4.2: color-picker swatch buttons showed the actual color only at their left/right edges, white in the middle where the "Renk seçin" text sits. Root cause: `width:100px !important` + `height:30px !important` (added to make the picker and "Clear" buttons equal-width) fought WordPress core's own internal color-chip positioning inside `.wp-color-result`, which assumes its own computed dimensions. Fixed by using `flex: 1 1 0` for equal-width sharing instead of forced fixed dimensions — WP's own width/height/padding math is left untouched. Also removed a now-redundant `width:100% !important` on the Button Styles cards' stacked pickers, relying on the flex column's own `align-items:stretch` instead.

## [2026-08-02] Typography Google Fonts system + CodeMirror (v1.3.11)
- Added `inc/typography.php`: an opt-in, per-element (H1-H6, paragraph) Google Fonts system exposed in GNN Panel → Typography. Off by default — self-hosted Space Grotesk/Manrope tokens (`--font-heading`/`--font-body`) are untouched and no extra request happens until enabled.
- When enabled, every configured family+weight is merged into ONE `fonts.googleapis.com/css2` request (never one per font), gated behind a shared preconnect (`gnn_google_fonts_preconnect()`, generalized from the existing Material Symbols preconnect to avoid duplicate `<link>` tags), with `display=swap`. Each role falls back to the theme default via CSS `var(--font-h1, var(--font-heading))` etc., so an unconfigured role costs nothing.
- No explicit "Latin Extended" toggle was added: Google's css2 endpoint already serves per-subset `@font-face` blocks gated by `unicode-range`, so the browser lazy-fetches the Turkish-glyph (ğ ı ş ö ü ç) subset automatically only when the page's actual text needs it — matching how the theme's own self-hosted fonts already work.
- Custom Code tab (custom_css / custom_js_head / custom_js_footer / head_html / body_html) now uses `wp_enqueue_code_editor()` / `wp.codeEditor` — WordPress core's own bundled CodeMirror, the same one behind Customizer → Additional CSS — for syntax highlighting. No third-party library added; gracefully falls back to a plain textarea if the site owner disabled the code editor in their WP profile.
- Dependency audit performed on request: confirmed the theme has no composer/npm dependencies, no bundled third-party JS libraries, and only three deliberately opt-in external calls (GitHub Releases API for updates, Material Symbols CDN, and now Typography's Google Fonts CDN) — all gated behind explicit user-enabled options, consistent with the "WordPress core + Elementor core" governance direction.

## [2026-08-02] Fix wrong top-level menu landing page (v1.3.15)
- User-reported bug: clicking the top-level "GNN" menu link landed on the Slider list, not the Theme panel. Root cause: WordPress registers CPT submenus in `wp-admin/menu.php` before the `admin_menu` action fires, so the Slider CPT's submenu claimed array index 0 under `gnn-panel` ahead of our own `gnn_panel_menu()` callback, and WordPress uses that first submenu entry as the top-level link's target. Fixed with `gnn_panel_menu_reorder()`, a late (`priority 999`) `admin_menu` hook that force-sorts `$submenu['gnn-panel']` so the Theme entry is always first, independent of core's registration order. See bug #36.
